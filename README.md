# SAP Finance Agent Cockpit · synthetic POC

An external finance agent calls approved SAP finance capabilities, checks the returned evidence and produces a month-end reconciliation. This is the **architecture story** shown by the demo. The runnable implementation is a Node-built, Fiori-inspired interface over a Python and SQLite simulator. Its three visible tabs are **Execution simulator**, **Live architecture**, and **Architecture pros & cons**. Evidence and architecture questions open through contextual links. Vendor names describe simulated boundaries. No SAP, AWS, Google, Databricks, BDC, Portkey or model account is connected.

**The cockpit hosts several agent modules.** Today: the Reconciliation agent (month-end S/4HANA versus Central Finance) and the Cash and Treasury Assistant (cash position, forecast, bank relationships and transfer proposals, modelled on what SAP documents for its Cash and Treasury agents). Each module has its own synthetic data, tools, ontology fragment and SAP references; the MCP route and hosting pages on the Architecture tab apply to all of them. A request is routed to the right module from its own words. A new agent is one file in `poc/agent_modules/`; see `docs/COCKPIT_ARCHITECTURE.md` (structure, contract, validation) and `docs/CASH_TREASURY_AGENT.md` (SAP findings and open points). The **Ontology** view under Architecture shows the concepts the agents work with, how they relate, which tools read or produce them and where SAP describes them.

The demo opens on a simulated Fiori-style **My Home** page. Select **Close & reconcile**, **Cash & treasury** or another agent tile to enter the cockpit, or select one of six **Open decisions** to go directly to its architecture flow, owner, next action and proof gates. The Home control returns to My Home. There is no real sign-in session. The shell, app tile and worklist are custom React/CSS, not SAPUI5 or an official SAP application. A footer on both levels states that the app is for demo and learning purposes only.

Inside the application, the Execution simulator follows a list-report pattern: a page header, finance KPIs, period and status filters, a full-width close worklist, and selected-period details. **Ask Finance Agent** opens a side panel instead of occupying the page by default. A nonzero variance is marked for review even when source snapshots are comparable. On shorter screens, the worklist scrolls within its own panel so the close summary stays visible.

The application shell has a working **Menu** for My Home, the three primary areas and the agent panel. Evidence and architecture questions open only through contextual links and have a return control. Agent replies offer contextual actions to open the reconciliation report, inspect source evidence and follow the component trace. The actions retain the synthetic case identifier so an older answer can reopen its own case.

The original v2 POC prompt established the synthetic architecture and finance controls. Later user requests superseded its two-tab layout with three primary tabs, later added a fourth **Architecture diagrams** tab and a fifth **MCP hosting & governance** tab, and added the decision lab, document investigation, compact landscape architecture, and Business report dialog. The original no-live-integration and no-real-posting boundaries still apply. Clear chat removes conversation messages only; it keeps the selected case and evidence. At 1440 × 900, the four primary tabs have equal width and the Business workspace uses internal pane scrolling. A compact landscape layout keeps all 12 architecture zones visible at 1536 × 720 CSS pixels, including a browser zoomed to 125% on a 1920 × 900 display.

## Run locally

`release/finance_reconciliation_local_windows.zip` is a clean Windows laptop bundle. Extract it to a writable folder and double-click `Start Finance Demo.cmd`. The first launch creates a local Python environment and installs the small `requirements-local.txt` web runtime; later launches reuse it. The browser opens the FastAPI version at `http://127.0.0.1:8876/`. The included `frontend/dist` assets work without Node or Git at runtime. See [local laptop guide](docs/LOCAL_LAPTOP_GUIDE.md) for prerequisites, port changes and the offline/package-index constraint. To rebuild the frontend after source edits, run `npm ci` and `npm run build` in `frontend`.

For a controlled presentation setup, the ZIP also includes four numbered Windows scripts: `01_Check_Prerequisites.cmd`, `02_Install_Local_Runtime.cmd`, `03_Run_Local_Demo.cmd` and `04_Verify_Local_Demo.cmd`. Run verification in a second window while the server stays open.

The hosted Streamlit My Home page also offers **Download Windows bundle**. Streamlit serves the versioned ZIP committed with the app; the displayed size and SHA-256 prefix help identify the download. This link appears only when the hosted bundle exists.

`py -3 local_demo.py --mode streamlit` or `run_streamlit.ps1` starts the **local** Streamlit version at `http://127.0.0.1:8502/`. It uses the same Node-built UI as a Streamlit custom component and an isolated in-memory SQLite fixture per viewer session. The compiled `frontend/dist_streamlit` assets are included so Streamlit Community Cloud will not need a Node build step. `requirements.txt` contains the Python dependencies for that entrypoint.

The existing public Streamlit deployment uses `streamlit_app.py` from GitHub. Local changes are not visible there until the repository is updated and Community Cloud rebuilds the app.

## Architecture team demo

1. From the simulated Finance Launchpad, open the cockpit, then select **Architecture** and **Live run**. Select a synthetic month, one of the three scenarios (S1 SAP-hosted hybrid, S2 AWS AgentCore-native, S3 AgentCore + Apigee hybrid) and a pace. Start the run. The external-agent view is a simulation driven by the local Python runtime: S1 calls Apigee, S2 calls AgentCore Gateway, S3 passes AgentCore Gateway and then Apigee.
2. Watch the five-stage journey advance from finance intent to external-agent invocation, SAP tool call, SAP evidence and deterministic reconciliation. Each state is derived from a persisted request or response event. The topology separates the external agent domain, SAP-owned finance path, enterprise data evidence and return. Select a zone, then open **Component trace** in Evidence for its purpose, owner, contract, bounded payload and live validation limit.
3. Load a stored case, replay, pause, or return to live state. The diagram uses a company-neutral projection: business identifiers and scope fields are removed before events reach this view.
4. In **Execution simulator**, ask `Reconcile February 2026`, `Why is there a variance?`, `Show source evidence`, `How does approval work?`, `Compare scenarios`, or a vendor/component question. The answer is deterministic or evidence-bounded. An unknown question gets an explicit limit rather than a fabricated result. Every follow-up records a component trace.
5. Use the month-end work center to review all 12 periods, three stale-source exceptions and the selected case. **Finance sources** in Evidence contains account balances, illustrative journal records, source snapshots and calculation inputs. November 2026 has a comparable $25,000 synthetic variance. February has a $0 match. For a comparable nonzero case, propose a signed variance marker; switch the demo role to finance approver to create a local `SYN-` marker receipt. This role switch is a simulation, not a security boundary.
6. For the agentic scenario, reconcile November 2026 and open the **Evidence & correlation** link. Select **Investigate variance**. The proof dossier updates through readiness, a gateway-routed four-document comparison, hypothesis testing and an action recommendation. The missing-document profile ties $1,000,000 in S/4HANA to $975,000 in Central Finance and identifies one $25,000 document. Select **Apply simulated reprocess and re-reconcile** to see the source and downstream evidence refresh and a new $0 reconciliation. Choose **Mapping conflict** on a fresh case to see the agent hold the action for review. The architecture tab shows the same persisted component events without company-specific scope.
7. Follow an **Architecture questions** link from My Home, Live run or Complete architecture, then click one of six open alignment questions; each shows what it means in the selected scenario. The Python evaluator shows up to 12 visual handoffs. Compare S1 SAP-hosted hybrid, S2 AWS AgentCore-native and **S3 AgentCore + Apigee hybrid** (preferred for SAP and non-SAP agents, not approved). Run denied probes for a missing target, missing SAP principal, unapproved write, unregistered tool or unapproved partner.

8. On a selected architecture question, open **Hosting & dependencies**. The implementation plan covers S1, S2 and S3 separately. Select a handoff to see its configuration work, prerequisites, accountable team and nonproduction acceptance proof. The side panel lists route-level open decisions and dependencies specific to the chosen question. The links lead to public AWS, Google and SAP product documentation; no tenant configuration or approval is implied.

The **Implementation** section in Evidence identifies the React/Node presentation, Python execution and SQLite event store. They power the simulator and are not separate agents. The live finance run offers all three scenarios: S1 and S3 call Apigee directly, S2 passes AgentCore Gateway and then Apigee.

The **Diagrams** tab holds ten generated vector diagrams (D1 enterprise AI reference, D2 to D4 the S1, S2 and S3 topologies, D5 four responsibility model, D6 AWS account and governance, D7 gateway and principal propagation, D8 cost and operational responsibility, D9 selection decision tree, D10 executive comparison) with a synchronized side-by-side mode. Each viewer supports wheel/pinch zoom, drag pan, +/− and keyboard controls, Reset to fit, 100%, an Expand view, opening the SVG full-size and SVG or 2x/4x PNG export. They are proposed designs, not tenant-verified architecture. See `docs/ARCHITECTURE_V5_2.md`.

The application has three primary areas. **Close & reconcile** is the finance user's home: simulated agent cards, the period worklist, the detailed reconciliation report and the Scenario lab. **Run & trace** replays a run through the live architecture. **Architecture decision** holds three views: **Compare options** (S1, S2, S3 and agent hosting), **Responsibilities & governance** (the MCP matrices, registry and evidence) and **Diagrams** (detailed L2 and landscape paths). Evidence and Architecture questions open on demand with a return control. Technical identifiers (trace and case ids, event counts, agent tool names) are hidden until you tick **Technical details** in the header; the long governance matrices are collapsed sections. Nothing was removed: every earlier tab is still reachable, and the old deep links still work.

**Agents.** The simulator screen shows seven simulated agents: Orchestrator, Scope & intake, Evidence, Variance & close, Investigator, Governance & route and Approval gatekeeper. Type a request (for example *Reconcile November 2026*) and the orchestrator plans deterministic steps and runs the read-only ones; clicking an agent or a step opens its layer with a banner. Agents are exposed as typed MCP-style tools (`GET /api/agent/catalog`, `POST /api/agent/plan`, `POST /api/agent/tools/{name}` and the `agent_plan` Streamlit action; code in `poc/agents.py`). They use deterministic rules, no LLM. The calls are in-process and MCP-shaped (there is no MCP transport). Posting to SAP, approval, investigation reprocess and data changes are deliberately not tools, and a posting request is refused. See `docs/AGENTIC_ARCHITECTURE.md`.

All architecture diagrams share one renderer (`renderTopology` in `frontend/src/mcpScenarios.js`) and one source: the canonical model `poc/architecture_model.py`, exported to `frontend/src/architectureModel.json` by `python scripts/build_architecture_model.py`. `node scripts/render_architecture_svgs.mjs <dir>` renders all ten and checks each against its specification.

The execution simulator now has a **Detailed reconciliation report** (summary, accounts, reconciling items, aging, controls, AI review, audit trail; CSV, JSON and print export) and a **Scenario lab** for synthetic close conditions. Both are driven by `poc/recon_report.py`; every table adds up to the S/4HANA versus Central Finance variance. SAP transaction names in it are references only and are never invoked.

**Spaces and pages (SAP Fiori style):** the shell has three spaces. **Finance apps** is a page of tiles, one per agent app: Close & reconcile, Cash & treasury and Accruals; a tile opens the app and a breadcrumb leads back. **Agents** has three pages: Ask the agents, Agent catalog (every agent as a tile, grouped by family) and Technical options (orchestration and calls, execution options, tool catalog). **Architecture & operations** is a page of tiles in four sections (Run and explore, Hosting and governance, Decide, Concepts and evidence) that open the architecture views. 

**Agents area and the accrual agent:** the Agents area is a SAP Fiori-style launchpad: every agent is a tile, grouped by family on tabs, with the technical options (orchestration, execution options, tool catalog) below. The first-level tabs are Close & reconcile, Cash & treasury, **Accruals**, Agents and Architecture. The **Accrual Posting Agent** imitates SAP's standard accruals agent on synthetic data at company-code level for five accrual types, with an Execution option (LLM, simulated, is the default; Rules is the alternative), review, approval, a simulated posting to a local synthetic ledger and reconciliation after posting. See `docs/ACCRUAL_POSTING_AGENT.md` and `docs/ACCRUAL_AGENT_REVIEW.md`.

**Architecture preference:** S1 is preferred for SAP-centric agents and S3 for agents that span SAP and non-SAP systems; S2 stays in the architecture for reference and is not preferred. Every architecture view shows it, and it is not an approval.

The **MCP hosting** tab explains how the Finance MCP is exposed, governed, hosted and executed in the three Architecture V5.2 scenarios: S1 SAP-hosted hybrid (Cloud Foundry agent, Apigee MCP, AWS Agent Registry for registration only), S2 AWS AgentCore-native (AgentCore Runtime agent and Gateway; Apigee optional) and S3 AgentCore + Apigee hybrid (AgentCore Runtime and Gateway fronting Apigee; a dedicated SAP-agent AWS account is proposed). S3 is preferred for SAP and non-SAP agents, conditional on account approval, identity validation, gateway interoperability and verified cost. The **Selection and cost** tab holds the recommendation evaluator, the gateway and identity comparison, an editable cost model with no invented rates, and the AWS account proposal. GitLab is the central platform that deploys everything; it is never a runtime. See `docs/ARCHITECTURE_V5_2.md`.

The **Complete architecture** page gives each of S1, S2 and S3 a one-screen overview (agent hosting, MCP gateway, custom MCP runtime, registries, LLM gateway, integration, authorization, persistence, unverified items and policy dependencies) and a side-by-side comparison of the 25 dimensions in the model. An Architecture diagram action opens the scenario's topology (D2 to D4) in the shared viewer. The **Agent hosting** page covers SAP BTP Cloud Foundry (S1) and AWS AgentCore Runtime (S2, S3) and states that registration is a separate decision.

**Presenting to an audience.** My Home has four audience lenses (enterprise architect, integration architect, finance, business architect), each linking to the three views that role needs. The Architecture area has a one-screen **Decision brief**: the proposed S1 baseline, seven open decisions with owners, and proof gates G1 to G7, none passed. Close & reconcile shows who does what in the close (system, agent, person) and the controls, until a report is selected. All of it is a proposal on synthetic data, not an approval.

**One selected period.** Level 1 (Close & reconcile) and Level 2 (Agents, detailed report) share one `YYYY-MM` selection that survives navigation, reruns and refresh, and every calculation receives it. A period without data says so instead of showing another month. The detailed report has a Matching details tab whose rows add up to the variance and an SAP posting guide for manual correction in SAP; see `docs/PERIOD_SYNC.md`.

## Data and verification

SQLite contains December 2025 through November 2026: 12 months, six synthetic G/L accounts, four source systems, 288 per-account balances and 144 journal evidence rows. The bounded seed uses one synthetic finance scope; it is not a document ingestion or arbitrary-company reconciliation service. The closing-balance rule is S/4HANA minus comparable Central Finance. BW/4HANA and Databricks provide freshness and context; an advisory model explanation never determines the amount.

The November investigation adds four synthetic replication comparison documents whose totals tie to the aggregate snapshots. The `sap.compare` operation follows the selected gateway, domain tool, SAP API Management, custom iFlow and Central Finance role path in the simulator. Each plan step persists evidence IDs, a SHA-256 digest and a decision. Once document investigation starts, the old case cannot create a variance marker. A simulated reprocess is an explicit local operator action; it is not SAP AIF execution or a balanced FI posting.

Run the Python suite with `python -m pytest -q tests/test_poc.py --basetemp=.pytest_tmp`. With the local web app on port 8899 and Streamlit on port 8612, run `python scripts/qa_current_release.py` for desktop and mobile Chromium checks of the current three-view interface. The earlier `qa_v3.py`, `qa_release.py`, `qa_agentic.py` and `qa_decision_lab.py` scripts are historical checks for prior layouts. `python scripts/package_streamlit.py` creates the allowlisted upload archive at `release/finance_architecture_streamlit.zip`. It contains the compiled Node-built interface, Python entrypoint, source modules, minimal pinned dependencies and an integrity manifest; it excludes local databases, environment files, screenshots and Node dependencies. The repository also includes the compiled Streamlit assets; select `streamlit_app.py` as the entrypoint for a separate deployment. See [architecture mapping](docs/ARCHITECTURE_MAPPING.md), [evidence](docs/DEMO_EVIDENCE.md) and [limitations](docs/POC_LIMITATIONS.md).

**Open decisions.** The Decision brief lists the five open architecture decisions with what the documents settle, what remains for the owner or tenant, options, a proposal and a proof; the matching checklist is `docs/POC_PROOF_AND_ENTITLEMENT_CHECKLIST.md`.

**Themes.** The header has a **Theme** selector with the standard SAP Fiori themes: SAP Quartz Light (default), SAP Morning Horizon, SAP Quartz Dark, SAP Evening Horizon, SAP High Contrast White and SAP High Contrast Black. The choice applies to every area and diagram and is remembered in the browser. The application is custom React rather than SAPUI5, so the themes are close approximations of the published theme families, not SAP's theme libraries. `python scripts/qa_themes.py` checks them on web, phone and Streamlit.
