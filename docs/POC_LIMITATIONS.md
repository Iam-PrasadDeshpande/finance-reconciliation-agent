# POC limitations and live validation gates

This application is a local simulator. Every vendor-named component is simulated in Python. No SAP, AWS, Google, Databricks, Portkey, BDC or n8n account is connected. A local class, simulated credential reference or SQLite record is not evidence of a deployed service or tenant capability. The posting API writes only a `SYN-` signed variance marker to local SQLite. It does not select debit/credit accounts, create a balanced FI document or change the source balances.

The one-process transport makes boundaries visible through the SQLite event log. It does not prove network isolation, distributed delivery, exactly-once behavior across crashes, vendor-native telemetry, or production-grade authentication. Synthetic sign-in and the maker/approver UI switch are role selectors; the same viewer can switch roles. Local SQLite events are persisted for replay; no external logs are shared. The approval callback is a local trusted-method simulation, not a signed webhook. The BDC reference points to the same Databricks evidence ID; it does not prove Delta Sharing or zero-copy interoperability.

The live map reflects local function-call events from the simulator. Demonstration pacing is deliberate synthetic latency, not a measurement of vendor service performance. The event stream can reconnect and replay stored events, while interrupted runs are marked on restart; this is not distributed recovery or a guarantee of complete delivery to every browser. The historical database is a bounded seed for one company code, one ledger, USD, six accounts and twelve monthly periods. Its journal rows are illustrative evidence; no detailed ledger accounting or document ingestion is performed. The business-question parser covers scoped reconciliation/variance/balance requests only and may ask for missing details. The local run worker has two threads and is not a production workload or authorization isolation boundary.

The architecture display removes company and ledger fields and recognized entity identifiers from its API event projection. This is a presentation redaction for a synthetic demo, not a security boundary for arbitrary uploaded data. The business workspace still uses the one documented synthetic finance scope. The Fiori-inspired tile layout is custom React/CSS; it is not SAPUI5 or a certified SAP Fiori application. Vendor component placement follows the reviewed v7 registry, while the visual route is an explanatory topology rather than measured network traffic. The separate SAP and Databricks paths are executed sequentially in the simulator.

The three demo views present finance outcomes, the neutral component path, and open architecture decisions. Detailed source snapshots, account and journal records, component messages, identity references and proof gates are collected in the Evidence & correlation view. The 1440 × 900 layout was checked for fit; narrower screens use local scrolling and stacked panels. Moving a record into Evidence changes its presentation, not the simulator's validation or security boundary.

The external-agent journey is a presentation of persisted local events. Its "agent invoked," "SAP tool call," and "SAP evidence" states do not establish a deployed agent, an MCP call, SAP Integration Suite traffic, or SAP backend authorization. The Python runtime executes a bounded fixed sequence; Node.js builds the frontend and is not a runtime agent. The Evidence Implementation section states these boundaries explicitly.

The bounded answer catalog covers reconciliation, variance explanation, source evidence and freshness, monthly history, approval state, scenario differences and common component questions. Every other question gets an explicit evidence limit and a component trace; there is no general-purpose document ingestion, retrieval service or live LLM. The FastAPI local app uses a persistent local SQLite file. The Streamlit variant uses session-isolated in-memory SQLite, so cases are lost when a viewer session ends or the app restarts. Neither variant has production authentication, multi-user finance authorization or durable hosted storage. A public Streamlit demo exists; publication does not establish any live vendor integration, and local changes require a separate repository update and redeploy.

The agentic November investigation is a bounded deterministic plan, not an autonomous general-purpose AI agent. Four seeded comparison documents tie to the initial S/4HANA and Central Finance snapshots. A selected fault profile creates either a mapped missing-document observation or a mapping-conflict observation. The synthetic `sap.compare` path and local reprocess action do not prove live Central Finance comparison reports, AIF status, iFlow behavior or SAP authorization. A successful local reprocess refreshes Central Finance, BW and Databricks synthetic balances together, then starts a new reconciliation; this does not model real replication scheduling, retries or cross-system transactionality. Proof hashes identify the local dossier payloads but are not external attestations or signed evidence. The architecture tab shows neutral proof references; the evidence tab shows synthetic document values and correlation.

The on-demand Architecture questions view is a separate decision simulator. Its S3 AgentCore-to-Apigee path is an **unapproved candidate** and does not update the v7 S1/S2 alternatives. The AI Foundry registry is shown as a design-time prerequisite, not a runtime network hop. Identity references, gateway handoffs, SAP authorization outcomes, partner onboarding and posting controls are generated from bounded Python rules; they are not Entra tokens, gateway calls, Cloud Connector traffic or backend role checks. Even a successful probe retains an OPEN decision and requires owner approval and tenant evidence. The downloaded JSON is a synthetic meeting packet, not an approval record. The conditional Cloud Connector node does not establish that every SAP target is on-premise.

The route hosting plans describe proposed prerequisites and acceptance proofs for S1, S2 and S3. They are architecture work items, not implemented connections. The AgentCore-to-Apigee MCP target example depends on an approved external endpoint, compatible protocol, network reachability, configured outbound identity and an explicit SAP principal strategy. The demo does not verify any of these against a tenant. Product documentation may change; the linked vendor references should be rechecked during implementation.

The first screen is a simulated Fiori-style My Home page, not an authenticated SAP session. Its Finance Reconciliation Agent tile opens the three-view application; each Open decision goes directly to its architecture flow, owner, proposed next action and proof gates; Home returns to My Home. These decisions are an architecture meeting baseline, not approvals or live system status. The app shell menu and answer actions navigate within the synthetic demo; they do not invoke a connected SAP Fiori launchpad. The Execution simulator uses a custom list-report layout with filters, worklist and selected-period detail; Ask Finance Agent opens a side panel. This is a visual imitation of Fiori floorplans, not an SAPUI5 application or accessibility certification. The desktop UI confines its three primary tabs to the viewport. Business records, long evidence and event lists scroll within their panels when needed. The architecture diagram presents 12 zones in compact landscape rows, while lower component records may require page scrolling on shorter displays. The Business report node opens a dialog with synthetic finance output, and the linked Evidence & correlation view contains detailed document values. Clear chat removes messages but retains the selected case and evidence.

The original v2 prompt's two-tab UX requirement was superseded by the later requests for three primary tabs with Evidence and Architecture questions available on demand. Its exhaustive per-component and per-edge drawer fields, transport-level isolation, unrestricted document/question handling and full zoom/filter controls are not all implemented in the current compact browser UI. The component and edge registries remain the architecture inventory, while the visible inspector shows a bounded subset and the chat returns explicit limits for unsupported questions. This POC should not be presented as satisfying every acceptance item in that original prompt.

| Gate | Status | Required live evidence before replacing a simulator |
| --- | --- | --- |
| G1 | OPEN | Scenario, owners, licensing, cost and network topology |
| G2 | OPEN | Selected gateway inbound authorization, target type and outbound credential proof |
| G3 | OPEN · P0 | Integration Suite/iFlow identity mapping and mapped SAP authorization at all three backends, or an approved service identity alternative |
| G4 | OPEN | Finance rules, source contracts, freshness and reconciliation vectors |
| G5 | OPEN · P0 | Human approval, reject/tamper/stale/duplicate/retry tests and nonproduction SAP document evidence |
| G6 | OPEN | Privacy, Unity Catalog grants, BDC sharing and Portkey retention |
| G7 | OPEN | Cross-system trace correlation, retention and incident ownership |

The Agent hosting shortlist is decision support only. It does not verify tenant entitlement, Region, model processing location, service plan, prices, workload limits or operational readiness. AgentCore Runtime, BTP Cloud Foundry/Kyma, Microsoft Foundry and Joule Studio references are documented product options, not live connections. The user-reported Joule Studio restriction remains an unresolved tenant applicability question. The S2 route deliberately selects an MCP-server target; AgentCore Runtime passthrough is a separate non-MCP Gateway design and is not interchangeable.
